# 拷问（grill-me）

把"我觉得差不多"的方案问成"每条都能验收"的方案。

## 什么时候用

- 需求还是一句模糊的话（"做个差不多的页面""支持一下算法"）
- 方案刚成型，还没被挑战过
- 准备交付/评审前，想先自己找一遍漏洞
- 用户明确说"拷问我""grill me""别客气"

**不适用**：事实查询、简单的代码修改、已经明确到可执行的指令。
对这些硬拷问只是浪费时间。

## 核心原则

**一次问一个问题，等回答再问下一个。**
一次性抛出十个问题是审讯，不是对话 —— 用户会挑着答，剩下的就漏了。

**每次都先复述我听到的，再问下一个。**
让用户有机会纠正我的理解，而不是在我错误的假设上继续追问。

**问到能写出验收条件为止。**
"能验收"的判据：这个问题的答案，能直接变成一条测试或一个检查项。

## 提问顺序（按这个顺序问，不要跳）

### 第一层：目标与边界

1. **这件事要解决谁的什么问题？**（不是"要做什么"，是"为谁解决什么"）
2. **不做会怎样？**（判断真需求还是伪需求）
3. **哪些明确不做？**（边界比功能更能防止跑偏）

### 第二层：可验收性

4. **怎么算做完了？** —— 要能写成一个可执行的检查
5. **如果做错了，怎么发现？** —— 有没有可观察的信号
6. **给一个具体的例子**：输入是什么、期望输出是什么

### 第三层：约束与风险

7. **环境/数据/权限有什么限制？**
8. **最坏情况会是什么？**
9. **有没有依赖别人的东西？**（对方做不出来怎么办）

### 第四层：方案本身

10. **这个方案里，哪个假设最脆弱？**
11. **有没有更简单的做法？**（能用 10 行解决就不要 200 行）
12. **如果要砍掉一半功能，砍哪些？**

## 判断"问够了"

同时满足三条就停：

| 条件 | 检查 |
|---|---|
| 目标可复述 | 我能用一句话说出"为谁解决什么" |
| 有验收条件 | 至少一条可执行检查 |
| 边界清楚 | 知道明确不做什么 |

**问不够就交付 = 把不确定性留给用户**。

## 输出格式

问完（或用户说"够了"）之后，给一份**结论摘要**：

```
目标：<一句话>
验收条件：
  1. <可执行检查>
  2. ...
明确不做：<列表>
最脆弱的假设：<一条> + <怎么验证它>
待定：<还没问到答案的，标出来>
```

**"待定"必须留出来** —— 假装所有问题都问清了，比不问更危险。

## 硬规则

- **不替用户做决定**。可以给建议并说明理由，但最终选择是他的。
- **不为了显得深刻而抬杠**。如果用户是对的，就明确说"这一点没问题"。
- **指出错误要具体**：说清哪一句错了、为什么错、正确的是什么。
- **不问已经明确的事**。用户已经说过的，不要再问一遍。
- **一次一个问题**。这条最容易被违反，也最重要。

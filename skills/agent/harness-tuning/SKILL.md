# 执行编排调优（harness-tuning）

借 Google Research **Harness²** 的框架：一个 agent 的表现不只取决于模型，
还取决于围着模型的**八个可编辑组件**。出问题时先定位是哪一层，
而不是一律"改提示词试试"。

> **本工程不引入 Harness² 本体**。它是 Linux + Python 3.12 + uv + 云认证的研究框架，
> 我们的场景是 Windows 离线桌面应用。这里只借它的**诊断框架**。

## 八个组件（按运行时角色分组）

| 构建上下文 | 定义工具接口 | 编排与中间件 |
|---|---|---|
| ① 系统提示 | ④ 工具说明 | ⑦ 子代理 |
| ② 护栏 | ⑤ 脚本 | ⑧ 插件 |
| ③ 记忆 | ⑥ 技能 | |
| ⑥ 技能（同时属前两组） | | |

本工程里分别对应：

| 组件 | 在本工程里是 | 文件 |
|---|---|---|
| ① 系统提示 | 告诉模型"数字只能来自工具"的那段 | `hc_agent/llm.py` 的 `SYSTEM_PROMPT` |
| ② 护栏 | 权限分级、动作白名单、永久禁用清单 | `hc_agent/policy.py` |
| ③ 记忆 | 会话历史、知识库检索上下文 | `chat_history.py`、`knowledge/` |
| ④ 工具说明 | 12 个函数的 schema 与 description | `llm.py` 的 `TOOLS` |
| ⑤ 脚本 | 确定性计算：容量搜索、复算、报告 | `capacity_search.py`、`pipeline.py` |
| ⑥ 技能 | 技能卡（人读）+ 技能契约（机读） | `skills/cards/`、`skills/contracts/` |
| ⑦ 子代理 | 本工程**未使用**（单进程确定性流程） | — |
| ⑧ 插件 | 桌面界面、引擎宿主、审计链 | `desktop/`、`engine_host.py` |

## 诊断流程：先定位，再改

**不要一上来就改提示词。** 按这个顺序排查：

```
现象：回答不准 / 不按预期行动
   │
   ├─ 它知道该做什么吗？ ── 不知道 → ① 系统提示 或 ④ 工具说明
   ├─ 它知道怎么调工具吗？ ─ 不知道 → ④ 工具说明（description 写清楚了吗）
   ├─ 它拿得到数据吗？ ───── 拿不到 → ③ 记忆（检索没命中？）或 ⑤ 脚本（算错）
   ├─ 它做了不该做的吗？ ─── 做了 → ② 护栏（权限/白名单漏了）
   └─ 流程本身错了吗？ ───── 错 → ⑥ 技能（步骤不可执行）或 ⑤ 脚本
```

**每一层都有独立的验证方式**：
- ①④ 看模型实际调了哪个工具、传了什么参数（`llm.ask` 的 tool 轨迹）
- ③ 看检索命中的 chunk（知识库「检索测试」页）
- ⑤ 看产物里的数字（对得上就是对的）
- ② 看动作是否被拒（`PolicyViolation`）

## 改进一次，只动一个组件

Harness² 的核心手法叫 **Propose–Probe–Compose**：

1. **Propose**：提出一处改动（只改一个组件）
2. **Probe**：在同一批问题上跑，看行为差异
3. **Compose**：差异支持才保留，否则回退

**一次改多处 → 不知道是哪处起的作用。** 这是最常见的错误。

### 在本工程里怎么 Probe

| 改的是 | 用什么测 |
|---|---|
| ① 系统提示 | 一组固定问题，看回答里数字是否仍与产物一致 |
| ④ 工具说明 | 看模型选对工具的比例（问"算例有什么元件"是否调 `inspect_dss_case`） |
| ③ 记忆 | 知识库 `run_eval`（已固化题目集，指标可复现） |
| ② 护栏 | `tests/verify_governance.py` |
| ⑤ 脚本 | 真实产物数字比对（FD002 333.984375 这类锚点） |
| ⑥ 技能 | `tests/verify_dev_doc.py` 的契约校验 |

**没有 Probe 的改动不要保留** —— 那是"感觉好点了"，不是"确实好了"。

## 本工程的硬约束（改动时必须守住）

| 约束 | 为什么 |
|---|---|
| 数字只能来自引擎或产物 | 模型自己算 = 违反核心红线 |
| `unknown` ≠ 不可行 | 二分搜索不能拿 unknown 当上界 |
| 越权抛异常，不返回 False | 静默失败会被当成"做完了" |
| 技能卡与契约必须配套 | 只写卡 = 机器调不了 |
| 动作必须登记 `ACTION_LEVELS` | 未登记默认拒绝 |
| 改完必须跑全量测试 | 现在 935 项，任何一处漂移都能抓到 |

## 输出格式

做一次调优后报告：

```
现象：<用户看到的症状>
定位：组件 <编号+名称>，依据 <怎么判断是这一层的>
改动：<只改了一处，具体是什么>
Probe：<用什么测的>，改前 <指标> → 改后 <指标>
结论：<保留 / 回退>，原因 <…>
未验证：<还有哪些没测>
```

**"未验证"这一栏必须留**，否则等于宣称全都测过了。

## 常见误判

1. **一切都归因于提示词**。多数问题在工具说明不清或脚本算错。
2. **一次改五处**。改好了也不知道为什么好。
3. **没有基线就改**。不知道改前后差多少。
4. **改了提示词但没跑数字一致性测试**。模型可能开始自己编数了。
5. **把护栏当成阻碍而绕过**。权限分级的每一层都对应真实事故。

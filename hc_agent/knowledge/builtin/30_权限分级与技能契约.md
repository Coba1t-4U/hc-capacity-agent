# 权限分级与技能契约

承载力结论要用于报备、审签、并网许可，所以除了"结果对不对"，
还要能回答两个治理问题：

1. **这个操作允许做吗？**（权限）
2. **这份结果有没有被改过？**（审计）

本章讲本工程怎么把这两件事做成可检查的机制。

## 一、为什么承载力评估需要治理层

| 普通问答场景 | 承载力评估场景 |
|---|---|
| 答错一句话，用户重问即可 | 结论可能进并网许可、影响投资决策 |
| 没有"谁批的"概念 | 必须知道谁签发、依据什么 |
| 记录丢了不要紧 | 记录丢了等于无法复现、无法追责 |

所以要有：**分级权限**（谁能签发）、**动作白名单**（能做什么）、
**哈希链审计**（记录没被改）。

## 二、四级权限

| 级别 | 名称 | 能做什么 | 不能做什么 |
|---|---|---|---|
| **L0** | 只读 | 看结果、算摘要、读报告、校验审计链 | 不跑任何计算 |
| **L1** | 离线仿真 | 跑潮流、跑容量搜索、做假设分析、独立复算 | 不出整改建议、不签发 |
| **L2** | 候选生成 | 出整改建议、出储能/调压方案候选、起草报告 | 不签发对外结论 |
| **L3** | 批准执行 | 签发容量结论、发布、签署报告 | 不能操作设备 |

**默认是 L1（离线仿真）**。原因：默认能算就够用了；
签发结论属于正式流程，应该显式提权，不该是默认行为。

**没有 L4**。本 Agent **永久不具备设备写操作能力** ——
这不是没做，而是刻意不做。承载力评估的结论必须经人签字才能执行。

## 三、动作白名单（默认拒绝）

每个动作都要在 `ACTION_LEVELS` 里登记，**没登记的一律拒绝**：

| 动作 | 最低权限 |
|---|---|
| `read_run`、`list_runs`、`summary`、`verify_audit_chain` | L0 |
| `analyze_opendss_case`、`what_if_dss_case`、`run_capacity_search` | L1 |
| `propose_remediation`、`propose_storage_sizing`、`draft_report` | L2 |
| `approve_capacity`、`publish_capacity`、`sign_report` | L3 |

永久禁用清单（写着代码里，不是口头承诺）：

```
write_device            写现场设备
send_control_command    下发控制命令
operate_switch          操作开关
adjust_tap_online       在线调分接头
close_dg_permit         直接签发并网许可
bypass_human_approval   绕过人工审批
```

**越权抛异常，不返回 False**。因为越权是**错误**，
静默返回 False 会被调用方当成"执行了但没结果"而忽略。

## 四、可执行技能契约

技能分两层：

| 层 | 文件 | 谁用 | 作用 |
|---|---|---|---|
| **技能卡** | `skills/cards/SK-*.md` | 人 | 评审、审计、培训 |
| **技能契约** | `skills/contracts/*/skill.json` | 机器 | 加载、权限校验、调用 |

契约示例：

```json
{
  "id": "HC.REMEDIATION.PROPOSE",
  "version": "1.0.0",
  "skill_code": "SK-13",
  "actions": ["propose_remediation"],
  "handler": "hc_agent.remediation:propose",
  "permission": "candidate_generation",
  "requires": ["binding_constraint"],
  "outputs": ["candidates", "disclaimer"],
  "auto_enabled": false
}
```

**加载时严格校验**，以下情况一律报错（不跳过）：
缺字段、ID 重复、动作重复、动作没在权限表登记、handler 模块/函数不存在。

为什么必须报错而不是跳过：跳过会让"技能明明没生效但界面显示正常"，
这是最难查的一类问题。

## 五、哈希链审计

普通日志挡不住篡改：谁都能改一行而不留痕。
**把每条事件的哈希指向上一条的哈希**，就得到一条链：

```
rec = {seq, event_id, run_id, action, status, actor,
       created_at, object_ref, detail, previous_hash}
event_hash = sha256(规范化 JSON(上述字段))
```

- 改任意一条的内容 → 该条哈希对不上；
- 删掉或插入一条 → 后续的 `previous_hash` 对不上。

校验结果给出**第一条断开的序号**，便于定位。

### 关键区分

| 校验的是 | 不校验 |
|---|---|
| 记录有没有被改动/插入/删除 | 结论本身对不对 |

**结论正确性由独立复算与人工审批负责**，两者不能互相替代。
回答时必须说清这一点，否则会让用户误以为"哈希通过 = 结论可靠"。

## 六、和规则包的关系

| 层 | 管什么 | 文件 |
|---|---|---|
| 规则包 | **数值**：限值、同时率、裕度 | `config/rules.yaml` |
| 权限策略 | **能不能做**：跑/出候选/签发 | `hc_agent/policy.py` |
| 技能契约 | **怎么做**：实现、输入、输出 | `skills/contracts/` |
| 审计链 | **有没有被改** | `audit/chain.jsonl` |

四层独立：换了规则包不代表能做更多动作，反之亦然。

## 七、在 Agent 里怎么用

| 问题 | 输出 |
|---|---|
| 电压越限了怎么办 | 整改候选（需 L2） |
| 这次运行有没有被改过 | 审计链校验结果（L0 即可） |

权限不够时，Agent 会明确说"需要候选生成权限"，
而不是悄悄给一个不完整的答案。

## 八、常见误区

1. **以为哈希通过就代表结论可靠**。只代表记录没被改。
2. **以为占了默认权限就能签发**。签发需显式提到 L3。
3. **把技能卡当成可执行代码**。卡是文档，契约才是可加载的。
4. **以为"没有 L4"是功能缺失**。是刻意的安全边界。
5. **补建审计链不记事件**。补建本身也应该留痕，否则等于"事后补的记录没痕迹"。

## 九、怎么核实

- 代码：`hc_agent/policy.py`（权限与白名单）、`hc_agent/audit_chain.py`（哈希链）、
  `hc_agent/skill_runtime.py`（契约加载与执行）
- 契约：`skills/contracts/*/skill.json`
- 技能卡：`skills/cards/SK-13/14/15` 为本轮新增
- 测试：`tests/verify_governance.py`（73 项）

# 常见疑问：容量为什么这么小 / 为什么是 0

## 容量为什么是 0 kW

说明**基线状态就已经越限**：不加任何新增容量，仅凭既有负荷与既有光伏，
就已经有约束不通过。此时接 1 kW 也不行，必须先治理基线问题。

排查顺序：

1. 看 `run_summary.json` 的 `binding_constraint`
2. 看 `binding_detail` 里的对象、实测值、限值、余量
3. 统计 `constraint_summary` 的 `fail` 与 `unknown` 数量

典型情况：线路负载率 136% 已经超 100% 限值 —— 这是热稳问题，
和新增光伏无关，是既有负荷已经过载。

## 管理值为什么比物理值小那么多

不是损耗，是管理口径。管理值 = 物理值 × 0.9（同时率）× 0.9（裕度）= 物理值 × 0.81。
少掉的 19% 是管理裕度。对外答复按管理值。

## 为什么等级是灰色而不是绿色

灰色是内部态，表示有未覆盖项或数据风险，**不能下发布结论**。
灰色不等于"没问题"，也不等于"有问题"，而是"还不能判定"。
处理办法：补齐缺失数据或扩展能力后重算。

## 为什么不同容量点上"卡住的原因"不一样

不同接入容量会触发不同约束。小容量时可能是某段线路先到载流上限，
稍大一些时可能变成末端电压先越限。所以"主导限制因素"是**针对最终容量点**而言的，
搜索过程中间点的卡点不一定是最终结论的卡点。

## 为什么复算通过了还是不能发布

发布需要三道门禁：独立复算、专业复核、审批。
复算只是第一道。常见状态是复算已过，但专业复核与审批尚未完成，
所以 `release_gate.passed` 为 false。这不是程序错误，是流程没走完。

## 为什么搜索轨迹里的 iteration 会重复

粗扫描与二分细化各自从 1 开始编号，所以序号会重复两次。
按 CSV 原始行序读才是真实调用顺序。

## unknown 到底算通过还是不通过

都不算。`unknown` 表示这项约束**没能算出结果**（能力未覆盖或数据缺失）。
它既不能当作通过来出容量，也不能当作不通过来否决。
存在 unknown 时必须在结论里单独声明覆盖情况。

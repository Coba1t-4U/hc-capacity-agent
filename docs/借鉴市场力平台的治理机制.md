# 从「市场力监测平台」借鉴了什么

参考了 `电力现货市场力监测与风险防控智能体平台_20261006` 的**架构做法**。
两个平台主题不同（电力现货市场力 ≠ 配网承载力），只吸收**治理机制**，
业务内容全部围绕配网承载力重写。

## 一、借鉴清单

| 借鉴点 | 该平台的做法 | 本工程落地 | 为什么对承载力有用 |
|---|---|---|---|
| **权限分级** | `PermissionLevel` 四级 + 动作白名单 | `hc_agent/policy.py` | 承载力结论要签发，必须分清"谁能出结论" |
| **默认拒绝** | 未登记动作不放行 | 同上 | 防新增功能被静默开放 |
| **永久禁用清单** | — | 同上（本工程新增） | 把"不操作设备"变成可检查的代码 |
| **哈希链审计** | `AuditLog` + `previous_hash` | `hc_agent/audit_chain.py` | 承载力结论要能证明"没被改过" |
| **可执行技能契约** | `skill.json` + 严格校验 | `hc_agent/skill_runtime.py` | 技能卡能评审，契约才能被运行时管控 |
| **按意图拆专业问题** | `questions.py` 把问题映射到"需要哪些前置分析" | `qa.py` 意图规则扩展 | 让"整改建议"成为独立能力 |

## 二、刻意**没有**借鉴的部分

| 该平台的 | 本工程 | 原因 |
|---|---|---|
| 案件（case）为中心的状态机 | 未引入 | 承载力的中心是"运行 + 规则包"，不是案件阶段 |
| 反事实重跑引擎（改报价重出清） | **部分借鉴**：`what_if_dss_case` 改光伏容量重跑潮流 | 形式相同，业务不同 |
| HHI/RSI 等市场力指标 | 不适用 | 与承载力无关 |
| 豁免/缓解方案评估 | 改为"整改措施候选" | 概念对应但内容重写 |
| Electron 桌面壳 | 继续用原生 Tk | 用户明确要求原生桌面，不是网页壳 |

## 三、四级权限（本工程的裁剪）

```
L0 只读          看结果、校验审计链
L1 离线仿真      跑潮流、跑搜索、做假设分析      ← 默认
L2 候选生成      出整改建议、起草报告
L3 批准执行      签发容量结论
（无 L4：永久不具备设备写操作能力）
```

**默认是 L1**。签发结论属于正式流程，应该显式提权。

永久禁用清单（写在代码里，可被测试检查）：

```
write_device / send_control_command / operate_switch
adjust_tap_online / close_dg_permit / bypass_human_approval
```

## 四、哈希链审计

原工程只有 `audit/events.jsonl`（业务事件，可被随意改）。
新增 `audit/chain.jsonl`：

```
event_hash = sha256(规范化JSON(seq, event_id, run_id, action,
                              status, actor, created_at,
                              object_ref, detail, previous_hash))
```

- 改内容 → 该条哈希对不上
- 删/插 → 后续 `previous_hash` 对不上
- 校验给出**第一条断开的序号**

**必须说清的边界**：校验的是**记录完整性**，不是**结论正确性**。
结论正确由独立复算与审批负责。回答时必须讲这一点。

老运行可一键补建（`seal_run`），补建幂等，原 `events.jsonl` 不改。
本机已给 FD002 / FD001 / APP001 补建并校验通过（各 10 条）。

## 五、新应用场景：整改建议候选

**问题**：承载力结论常是"不能再接了"，用户下一句必然是"那我能做什么"。

**做法**：`hc_agent/remediation.py` 按**真正触发的约束**给候选：

| 约束 | 候选 |
|---|---|
| 电压 | RM-V-01 缩短半径/加粗截面、RM-V-02 调分接头、RM-V-03 逆变器无功 |
| 载流 | RM-T-01 限接入/分批、RM-T-02 配变增容/分流 |
| 反向潮流 | RM-C-01 配储能、RM-C-02 需求响应 |
| 不平衡 | RM-B-01 调整单相相别 |
| 短路 | RM-S-01 专项校核后再定接法 |

每条都带四要素：**为什么有效 / 效果 / 局限 / 依据**。

**关键边界**：
- 只为**越限的约束**出候选（没越限不出，避免列一堆无关方案）；
- **不给改造后的承载力数字**（需重新建模 + 容量搜索）；
- **不做经济性比较**；
- 输出是"候选方向"，不是"整改结论"。

## 六、顺带修掉的四个真实缺陷（做评估测试时暴露）

为了给知识库做**可复现**的回归，发现评估模块有四个问题：

1. **评估集每次重抽题**：`run_eval` 每次调 `generate_eval` 随机抽 30 块。
   文档 21→30 篇后 hit@3 在 0.53~0.93 乱跳，看着像检索坏了，其实是题目换了。
   → 改为**生成一次后落盘复用**（`stable=True` 默认）。

2. **显式题目不落盘**：传 `items=` 时 `path` 为空，下游读文件直接 `PermissionError`。
   → 显式题目也写文件。

3. **`it["source"]` 硬依赖**：调用方给的题目没有该字段就崩。
   → 改为 `.get()` 并兜底到 topic。

4. **`note` 不随结果返回**：口径声明只写在文件里，界面拿不到。
   → 改为随结果返回，且显式分支也有兜底文案。

另外测试侧发现：`doc_id` 是**每次建库随机生成**的（`doc_021db0a7d0e2` 这种），
按它排序取题等于随机取题。改用**文档标题 + 标题路径**排序，指标才真正可复现
（连跑 6 次完全一致）。

## 七、验证

- **审计链**：正常通过、改内容定位到第 3 条、删行判 previous_hash 不匹配、

  未登记动作默认拒绝、越权抛异常（不是静默 False）、
  元数据非法值回落默认（不静默提权）

  L1 执行 L2 技能被拒、L2 执行成功、缺必需输入明确报错、L0 可跑只读技能
- **整改建议**：电压/载流各给对应类候选、每条四要素齐、带免责声明、
  没越限不给候选、多约束都给、能从真实运行出候选
- **问答接线**：5 个新意图正确、4 个原有意图不被抢走、回答含候选编号与边界声明

# 独立分发（PyInstaller 打包）

> 产物：`release/HC-Agent-1.0.0-win64-<日期>.zip` 约 **75 MB**，解压后 **204 MB**
> 解压后双击 `启动 HC-Agent.bat` 即可运行，**目标机器不需要装 Python**。

## 一、构建

```bash
python tools/build_release.py
```

脚本做五件事，任一步不合格就中止（**不合格的产物不打包**）：

1. **清洁重建**（`--clean`）—— 不加这个参数会拿到上一次的 exe。
   本项目实测踩过：改了代码但产物没变，白排查半小时。
2. 把启动器与 `使用说明.md` 拷进产物目录。
3. **产物自检**：跑 `--self-test`，检查可写目录 / 引擎 / numpy。
4. 统计体积与文件数。
5. 打 zip 并输出 SHA256。

其它用法：

```bash
python tools/build_release.py --no-zip       # 只构建
python tools/build_release.py --skip-build   # 只重打包
```

## 二、关键打包决策

### onedir 而非 onefile

引擎 DLL 约 74 MB（`dss_capi.dll` + numpy + OpenBLAS）。onefile 每次启动都要解压
到临时目录，冷启动多花 10~20 秒，退出清理失败还会在临时目录堆积。onedir 一次
解压，启动快得多。代价是一个文件夹而不是单文件。

### 引擎 DLL 必须显式收集

OpenDSS **不在 site-packages 里**，而在工作区 `opendss_demo/pylibs`。
PyInstaller 的依赖分析看不到它们。不显式收集的后果很阴险：
**打包成功、启动正常，但一跑计算就 `DLL load failed`** —— 在开发机上完全复现不了。

spec 里还排除了调试版（`*d` 结尾）与 `.lib`/`.a` 链接期文件，省约 36 MB。
依据是实测：`import dss` 只加载 `_dss_capi.pyd` → `dss_capi.dll`。

### numpy 的 OpenBLAS 是延迟加载

`_multiarray_umath.pyd` 依赖 `libscipy_openblas64_*.dll`，PyInstaller 解析不到，
只会在日志里给一句 `Library not found`。后果是：**numpy 完全无法导入 → 所有引擎
通道探测失败 → 静默降级到 CLI 通道**。界面看起来"能用"，但走的是低精度通道。

所以 spec 里把 `numpy.libs/*.dll` 显式放进 `binaries`（不是 `datas`），确保它们
位于加载器可见的目录。

### 不启用 UPX

UPX 会破坏部分 DLL 的签名/加载，引擎 DLL 尤其敏感。

## 三、冻结模式的适配

打包后 `__file__` 指向 `_internal`，所有 `Path(__file__).parents[N]` 都会指错。
因此新增 `hc_agent/paths.py` 作为**唯一入口**：

| 函数 | 源码模式 | 打包模式 |
|---|---|---|
| `bundle_root()` | 仓库根 | `sys._MEIPASS`（`_internal`） |
| `data_root()` | 仓库根 | `%LOCALAPPDATA%\HC-Agent` |
| `runs_root()` | 仓库根/runs | `data_root/runs` |

**只读资源与可写目录必须分开**：安装目录通常不可写（Program Files），且升级会
覆盖用户数据。

`data_root_safe()` 会**逐级降级**：首选 → 用户主目录 → 临时目录。
注意 `os.access` 在这类场景会给出乐观答案（实测：报 true 但 mkdir 抛 WinError 5），
所以它实现方式是**真的建一次目录**再清理。

### 子进程：同一个 exe，不同开关

打包后 `sys.executable` 就是本程序，`python -m hc_agent.engine_host` 会**再开一个
界面**。所以入口按参数分派：

```
HC-Agent.exe                 桌面 GUI
HC-Agent.exe --engine-host   引擎宿主（子进程）
HC-Agent.exe --self-test     自检
HC-Agent.exe --paths         路径诊断
```

## 四、踩过并修掉的坑

| 问题 | 现象 | 根因与修法 |
|---|---|---|
| **stdout 污染协议** | `run_task` 的应答被进度行冲掉，界面"卡住" | `Pipeline.say()` 用 `print()` 写 stdout，而子进程的 stdout 是行分隔 JSON 协议。改走 stderr |
| **numpy 导入失败** | 引擎通道 0/3，静默降级到 CLI | OpenBLAS DLL 未进包。显式收集 `numpy.libs/*.dll` |
| **`--clean` 缺失** | 改了代码产物没变，白排查 | 构建脚本强制 `--clean` |
| **`SPECPATH` 用法错** | `script not found` | `SPECPATH` 是 spec 所在目录，要用 `.parent` |
| **PowerShell 写文件加 BOM** | `SyntaxError: invalid non-printable character U+FEFF` | 写脚本/配置后检查并剥离 BOM |
| **`start "" /d "<含空格路径>"` 无效** | 启动器静默不启动 | 目录含空格时 `/d` 不可靠；改 `cd /d` 后直接 `start "" "%EXE%"` |
| **并发建目录竞态** | 首次运行 `PermissionError WinError 5` | GUI 与子进程同时创建数据目录。`ensure_writable` 加重试与复核 |
| **数据目录不可写** | 首次运行直接失败 | `data_root_safe()` 三级降级 |
| **windowed 无 stderr** | 启动失败毫无线索 | 加 `HC_TRACE=1` 开关，启动过程写 `logs/gui-trace.log` 与 `backend-trace.log` |

## 五、验证

```bash
python tests/verify_package.py        # 18 项：冻结路径 / 资源 / 引擎 DLL / 真实求解
python tests/verify_packaged_gui.py   #  4 项：打包 GUI 真的能开窗且内容非空白
```

`verify_package.py` 里最关键的一条是**真的跑一次求解并核对容量值**（333.984 kW）——
能加载 DLL 不等于能算出正确结果。

已实测的干净环境验证：**解压 zip → 清空所有 `HC_*` 环境变量 → 换 cwd →
自检通过、真实求解 333.984375 kW / green、GUI 正常拉起 2 个进程**。

## 六、已知限制

* **只支持 Windows x64**：spec 未做跨平台配置。若要 macOS/Linux 需另配。
* **未签名**：Windows SmartScreen 首次运行可能提示"未知发布者"。要消除需
  代码签名证书。
* **目录必须完整复制**：`_internal\` 不能漏，否则引擎加载失败。
  界面上会显示引擎 0/3，`--self-test` 也会明确报错。
* **不支持自动更新**：新版本需手动替换目录。

## 一、移植了哪些（含为什么）

### 1. 引擎多通道 + 自动降级（`hc_agent/engines/engine_channels.py`）

**为什么搬**：本工程原本只有一条通道（OpenDSSDirect 进程内调用）。实测过它的
风险——天枢一号用进程内 `dss-python` 起 HTTP 服务时，`POST /api/run` 会让
uvicorn 进程**无 traceback 直接消失**（原生崩溃）；换 CLI 通道后同一请求成功。
本工程若那条唯一通道出问题，同样没有退路。

**搬了什么**：三通道定义（`opendssdirect` / `dss-python` / `cli`）、
可用性探测、按需降级、**通道能力显式声明**。

**关键设计**：`ChannelCapability` 把"这条路给不了你什么"写进类型里——
CLI 通道 `significant_digits=6`、`min_reliable_tolerance=1e-5`、不支持 Python
回调。这样"用 CLI 的结果去做 1e-6 容差的复算比对"会在选择阶段就被拒绝，
而不是安静地跑出一个看似正常的错误结论。

### 2. 崩溃可观测（`hc_agent/runtime/crashlog.py`）

**为什么搬**：本工程的长任务崩溃后只有"进程没了"，查不到死在哪一步。

**搬了什么**：三个钩子（`excepthook` / `threading.excepthook` /
`sys.unraisablehook`）**且每个都链回原钩子**（绝不吞异常）、fsync 落盘、
单代轮转、`write_errors` 计数、幂等安装。

**必须诚实声明的局限**（天枢一号源码自己承认，我照抄这个诚实度）：
**Python 抓不到原生段错误**。所谓"原生崩溃可观测"实际只到
"退出码 + 最后落盘阶段"这一层，没有 faulthandler / minidump。

### 3. 状态增量落盘（`hc_agent/runtime/state_store.py`）

**为什么搬**：`checkpoints.json` 是**累积列表且非原子写**——进程被 Kill 时可能
留下半截 JSON，比没有文件更难排查。

**搬了什么**：`.tmp` → `fsync` → `os.replace` 的原子写；`_persisted_stage` /
`_persisted_at` 遗言字段；**两者都保留**（`checkpoints.json` 给人看历史，
`state.json` 给机器读最新遗言）。

**顺手修掉的一个真问题**：本工程 `evidence.write_json` 用的是
`Path.write_text`——非原子、无 fsync。已另加 `write_json_atomic`。

### 4. 新增 `interrupted` 终态（`errors.py`）

**为什么**：本工程原本只有 `exit_code`，没有"**没来得及下结论**"的语义。
天枢一号把这个理由写得很清楚，值得照搬：

- `SYSTEM_FAILED` 排查看错误码；`INTERRUPTED` 排查看崩溃日志与最后落盘阶段；
- 归入 `unknown` 更糟——会让看板把基础设施问题混进业务分布，成功率分子分母
  都被污染。

### 5. 求解口径声明表（`hc_agent/reporting.py`）

**为什么搬**：本工程报告只有散文式"风险与缺口"，缺逐项口径声明。天枢一号的
「本次求解口径声明」把求解模式、三相建模、负荷模型、单位口径、未覆盖范围
逐项列成表——正是设计文档要求的"报告注明求解范围、场景覆盖、未支持分析、
模型假设、精度和有效期"。

### 6. 算例格式转换器（`hc_agent/io/converters.py`）

**只搬数值裁定，不搬管道**（详见第三节）。

## 二、**没有**搬的（以及为什么）

| 组件 | 不搬的理由 |
|---|---|
| `build_dss_from_frames` 单体函数 | 它输出单个扁平 `Master.dss`；本工程是多文件 + `Redirect` + 绝对路径。架构相反，无法调和 |
| 列名别名表 | 本工程输入契约是固定英文表头并由 `IssueCollector` 校验。采纳别名会**削弱** schema 纪律 |
| `os._exit(70)` → Electron 重启闭环 | **退出码 70 只有在"外层有重启者"时才有意义**。孤立使用只会让任务静默消失，比不退出更糟 |
| `_ComWorker` 代次重建自愈 | 专为 COM 单线程 STA 设计。本工程用 `dss.NewContext()` 每实例独立上下文，该模型不成立 |
| 任务级 resume | **天枢一号也没有**。它的"恢复"仅指进程重启，不指续跑。要做属于新增设计 |
| `MVAsc3/MVAsc1 = S_base×1e6` | 占位符，其自身文档承认不是短路计算 |

## 三、从转换器搬来的「数值裁定」（本项目专属价值）

这些是**物理规律**，与本工程输入格式无关，照搬：

| 裁定 | 值 | 源码记录的证据 |
|---|---|---|
| **变压器 kVA 基准取系统基准**，不用 `rateA` | `xfmr_kva = s_base_mva * 1000` | 用 MATPOWER `rateA` 作基准会让变压器等值阻抗放大 **1.8~5.6 倍**，最低电压从参考 0.900 崩到 **0.787** |
| **串联 `%Rs` 对半拆** | `r_pct = r_pu*100/2` | OpenDSS 双绕组串联 R 是两绕组之和；不拆 = 电阻翻倍 |
| **`XHL` 不拆** | `x_pct = x_pu*100` | XHL 已是总漏抗百分值 |
| **单相负荷 kV = 线电压/√3** | 2φ/3φ 用线电压 | 输入 `base_kv` 恒为线电压；单相负荷的 OpenDSS `kV` 是相电压，不除 √3 会把负荷高估 √3 倍 |
| **`b_pu → C1(nF)`** | `C = (b_pu/Z_base)/(2πf)·1e9`，`Units=none` | 整条线路总电容 |
| **零阻抗判定 `1e-12` 且 r/x 双双小于** | `abs(r)<1e-12 and abs(x)<1e-12` | **只拦严格为零**；1e-9 pu 是合法数据，交给求解器按容差处理 |
| **`Vg` 覆盖 `Vm`** | 发电机母线 | MATPOWER `row[5]`(Vg) 覆盖 `row[7]`(Vm) |
| **PV → `Model=3` + `Vpu`；PQ → `Model=1`** | — | 全部写 `Model=1` 会让 `Vpu` 失效，case03 最低电压偏低 0.04 pu |
| **频率从算例读，不写死** | `FREQUENCY_HZ` | 影响充电电纳→电容换算 |
| **Q 限值默认不强制** | `enforce_q_limits` 默认关 | 参考解是"无约束 PV-Q"；表格算例给 ±5 MVAr 配 1117 MW 负荷，会把 PV 降为 PQ 并系统性压低电压（实测 vmin 0.79 vs 参考 0.895） |
| **变压器判别以物理事实优先** | `kv_differs or kind in {...}` | 曾把 `tie` 类型静默当成 110 kV→20 kV "线路" |

**同时也记录它的问题，本工程不照抄**：
- 它**从不写负荷 `Model`/`Vminpu`**，其自身测试把"沿用 OpenDSS 默认 0.95 会隐性转恒阻抗"标为**已知未决项**。本工程显式写 `model=1`（更好），但应进一步显式写 `vminpu`。
- `_to_float(..., default)` 会把畸形数值吞成默认值（`r_pu="abc"` → 0.005）。本工程 `as_float` 返回 `None` 并阻断，**保持本工程做法**。
- 零阻抗报错信息恒说 "pu"，即便该行给的是欧姆。本工程按单位分别措辞。

## 四、移植时同时补上的本工程原有缺陷

移植过程暴露了本工程自己的几个问题，一并修掉：

| 缺陷 | 影响 | 修法 |
|---|---|---|
| 单相负荷用线电压 | 单相负荷被高估 √3 倍 | `build_model.py` 按相别决定 `kV`，与天枢一号 `load_kv_for_nodes` 对齐 |
| `write_json` 非原子 | 进程被 Kill 时留半截 JSON | 新增 `write_json_atomic`（tmp + fsync + replace） |
| 变压器阻抗**无条件** `XHL=√(Z²−R²)` | 见下 |
| 缺 `interrupted` 语义 | 无法区分"判失败"与"没来得及判" | 新增 `EXIT_INTERRUPTED = 6` |

**关于变压器阻抗的说明**：本工程原实现由 `vk_percent`/`vkr_percent` 反算
`X = √(Z²−R²)`，这在**输入给的是短路阻抗百分值**时是正确的（GB 标准台账就是
这么给的）。天枢一号的规则适用于**输入给的是标幺阻抗**（MATPOWER 场景）。
两者不冲突——本工程据此**分流处理**：给了 `vk/vkr` 走原路径；给了 `r_pu/x_pu`
才用 `%Rs 对半 / XHL 不拆` 的规则。
